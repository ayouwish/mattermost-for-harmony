## Goal

Make the Mattermost HarmonyOS app render (login screen visible) by fixing the RNOH bundle build pipeline, then verify the existing MVP screens work end-to-end against a real Mattermost server. Do NOT build new feature modules in this plan — that is a follow-up.

## Scope / Non-goals

**In scope:**
- Fix `metro.config.harmony.js` to use `createHarmonyMetroConfig`.
- Add a root `react-native.config.js` to register the `harmony` platform + `bundle-harmony` command.
- Fix `package.json` bundle script output paths (they currently write to a nonexistent `harmony/entry/...`).
- Regenerate `entry/src/main/resources/rawfile/bundle.harmony.js` correctly.
- Rebuild HAP, deploy, and verify RN renders (no more `[runtime not ready]: TypeError: Cannot read property 'select'`).
- End-to-end smoke test: Login → ChannelList → send/receive a message on the user's real server.

**Non-goals (explicitly deferred):**
- Implementing any of the 15 modules in `mattermost-client-core-features.md` (Phase 1 features, threads, search, emoji, etc.).
- Rewriting `src/` app code beyond minimal touch-ups needed to render (e.g. guarding RNOH-unsupported APIs if any surface during testing).
- Network/permission issues unrelated to rendering (cleartext HTTP, websocket reachability) unless they block the smoke test.

## Current State And Constraints

**Confirmed root cause (from log + bundle inspection):**
- HiLog shows: `__█__ [runtime not ready]: TypeError: Cannot read property 'select' of undefined` at `bundle.harmony.js 88` (= `BridgelessUIManager.js`), plus a follow-up `Cannot read property 'default' of undefined`.
- Bundle inspection: module 63 (`Platform.js` shim) has a self-reference `__d(..., 63, [1, 63])` → `Platform` is `undefined` at runtime. The harmony impl `Platform.harmony.ts` (`OS: 'harmony'`, real `select`) is **not in the bundle** (`grep "OS:'harmony'"` → 0 matches).
- `metro.config.harmony.js:9-22` only adds `harmony.*` to `sourceExts`; it does **not** call `createHarmonyMetroConfig`. The custom `resolveRequest` that rewrites `react-native` → `@react-native-oh/react-native-harmony` is never installed.

**Pipeline gaps (both confirmed present):**
1. `metro.config.harmony.js` missing `createHarmonyMetroConfig` — `node_modules/@react-native-oh/react-native-harmony/metro.config.js:33` exports it; project does not use it.
2. No root `react-native.config.js` (glob returned none) — so the `harmony` platform and `bundle-harmony` command (`node_modules/@react-native-oh/react-native-harmony/react-native.config.js:32-41`) are not registered.
3. `package.json:12-13` scripts write to `harmony/entry/src/main/resources/rawfile/...` but that subtree doesn't exist; the app reads from `entry/src/main/resources/rawfile/bundle.harmony.js`.

**What is already correct (verified, do not touch):**
- Version pairing: `react-native@0.84.1` + `react@19.2.3` + `@react-native-oh/react-native-harmony@0.84.2` (CHANGELOG + peerDeps confirm 0.84.1 pairing).
- ArkTS side: `entry/src/main/ets/pages/Index.ets` uses `RNApp` + `ResourceJSBundleProvider('bundle.harmony.js')`; `EntryAbility.ets` extends `RNAbility` returning `'pages/Index'`; `appKey` `'MattermostHarmonyOS'` matches `app.json` and the bundle's `AppRegistry.registerComponent` name.
- Native libs (librnoh_app.so + core) are built and packaged.

**Constraints:**
- ArkTS strictness does not apply (no `.ets` edits in scope).
- The two metro configs serve different commands: `metro.config.js` (default, used by `react-native start`) and `metro.config.harmony.js` (used by `bundle`/`start --harmony`). Both should be harmony-aware to avoid confusion.
- The user has a real Mattermost server URL; smoke test needs network egress from the device (HTTP + WS). If cleartext/permission issues appear, treat as a follow-up but note them.

## Design

### Step 1 — Rewrite `metro.config.harmony.js` to use `createHarmonyMetroConfig`
Replace the hand-rolled config with the canonical RNOH config. This installs the `resolveRequest` hook that rewrites `react-native` → `@react-native-oh/react-native-harmony`, injects `InitializeCore` (harmony) pre-main, pins `assetRegistryPath`, and handles `@react-native/virtualized-lists` patching (relevant for the FlatList used in ChannelListScreen/ChatScreen).

```js
const { getDefaultConfig, mergeConfig } = require('@react-native/metro-config');
const { createHarmonyMetroConfig } = require('@react-native-oh/react-native-harmony/metro.config');

module.exports = mergeConfig(
  getDefaultConfig(__dirname),
  createHarmonyMetroConfig({ reactNativeHarmonyPackageName: '@react-native-oh/react-native-harmony' })
);
```

The scoped package name must be passed explicitly because `createHarmonyMetroConfig` defaults to `'react-native-harmony'` (`metro.config.js:37-38`) for backward compat.

### Step 2 — Add root `react-native.config.js`
Register the `harmony` platform and the `bundle-harmony` command by re-using the config already shipped in the harmony package. Minimal root config:

```js
module.exports = {
  ...require('@react-native-oh/react-native-harmony/react-native.config.js'),
};
```

This spreads in `platforms.harmony` + `commands` (which pulls `bundle-harmony` from `@react-native-oh/react-native-harmony-cli`). This enables both `react-native bundle-harmony` and correct platform resolution for `react-native bundle --platform harmony`.

### Step 3 — Fix `package.json` bundle script paths + use `bundle-harmony`
Switch the scripts to the canonical command and point output at the real rawfile consumed by the app:

```jsonc
"bundle:harmony": "react-native bundle-harmony --dev false --entry-file index.js --bundle-output entry/src/main/resources/rawfile/bundle.harmony.js --assets-dest entry/src/main/resources/rawfile/assets --config metro.config.harmony.js",
"bundle:harmony:dev": "react-native bundle-harmony --dev true --entry-file index.js --bundle-output entry/src/main/resources/rawfile/bundle.harmony.js --assets-dest entry/src/main/resources/rawfile/assets --config metro.config.harmony.js"
```

Rationale: `bundle-harmony` sets `platform: 'harmony'` internally (`bundle-harmony.js:72`) and handles asset copying via its own resolver; the standard `bundle --platform harmony` works too once the metro resolver is fixed, but `bundle-harmony` is the canonical path and avoids edge cases. Output path must be `entry/src/main/resources/rawfile/` (where Index.ets reads from), not the nonexistent `harmony/entry/...`.

### Step 4 — Also align `metro.config.js` (default) for harmony
So that `react-native start` (dev server / Metro) also resolves harmony correctly. Same content as Step 1 applied to `metro.config.js`. (Optional but recommended for consistency; avoids a second black-screen class of bug when debugging via Metro.)

### Step 5 — Regenerate bundle, rebuild HAP, deploy, verify
- Run `npm run bundle:harmony` (or `bundle:harmony:dev`).
- Verify `entry/src/main/resources/rawfile/bundle.harmony.js` is regenerated and **now contains** `OS:'harmony'` / `PlatformConstants` / `getEnforcing('PlatformConstants')` (quick `grep` sanity check — these were absent before).
- Build the HAP (`build_project`), deploy to the MatePad Pro (`start_app`).
- Collect HiLog (`hdc_log`) and confirm:
  - No more `Cannot read property 'select' of undefined`.
  - `Running "MattermostHarmonyOS"` appears, then the Login screen renders.
- Smoke test against the user's real server: connect → login → channel list loads → open a channel → send a message → receive a message via WebSocket.

### Risk-handling during verification
- If a different JS error surfaces after Platform is fixed (e.g. a specific component not implemented in RNOH), capture the new stack from HiLog and address it minimally — do NOT expand into feature work.
- If WebSocket can't connect (e.g. cleartext/wss), that is a network/permission follow-up; the Login + ChannelList REST path can still validate the render fix.
- If `bundle-harmony` errors on `colors`/`fs-extra` missing deps, fall back to `react-native bundle --platform harmony --config metro.config.harmony.js` (the fixed metro resolver is the actual fix; `bundle-harmony` is convenience).

## Risks And Compatibility

- **`bundle-harmony` runtime deps**: the command requires `colors`, `fs-extra` (transitively). These are usually pulled by the CLI install; if absent, fall back to `react-native bundle --platform harmony --config metro.config.harmony.js` — the resolver fix is the essential part.
- **Secondary JS errors**: once Platform works, another RNOH-unsupported API (e.g. a KeyboardAvoidingView quirk) could surface. Mitigation: capture HiLog, patch minimally, do not scope-creep.
- **Network egress**: real-server smoke test may hit cleartext-HTTP or self-signed-cert restrictions on the device. This is orthogonal to the render fix; if it blocks login, note as follow-up (likely needs `module.json5` network config / certificate handling), but the render fix itself is still proven by the login screen appearing.
- **Metro `inlineRequires`**: the circular self-reference in the old Platform shim was masked/unmasked by `inlineRequires: true`; the canonical config keeps `inlineRequires: true` (`metro.config.js:53`), so the real fix is the resolver, not a transform flag.
- No SDK/permission changes in scope.

## Rollback

All changes are JS-tooling only (no native code). To revert:
1. `git checkout metro.config.harmony.js metro.config.js package.json` (restore prior configs/scripts).
2. `rm react-native.config.js` (it's a new file).
3. Regenerate the old bundle or restore the previous `bundle.harmony.js` from git (if tracked) / leave the current one.
4. Rebuild HAP.

No ArkTS, CMake, or `module.json5` changes were made in this plan, so no native rollback is needed.
